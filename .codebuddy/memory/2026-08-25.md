- 对“刷新按钮先并行刷新未提交与提交，再异步刷新仓库和分支，支持打断重启”的评估：取消只可阻止旧结果落地，不能使错误依赖顺序正确。前两项仍读取旧 HEAD/旧分支；随后仓库扫描会更换仓库快照，分支读取应等待该快照，且分支选择变化会取消并重启提交读取。正确刷新事务应从仓库快照开始，随后等待 HEAD/分支选择快照；working-tree status 可与完整分支列表并行，提交列表只能在分支选择落地后启动。每轮以同一 refresh generation 取消上一轮并防止旧轮发布。

- 快速并行刷新风险边界：同一仓库的 `git status` 与 `git log` 会争抢磁盘、对象库和 OneDrive/防病毒扫描资源，慢仓库未必更快；status 读取可能引发 `.git/index` watcher，现有 watcher slot 会合并再读；点击瞬间的 refs 与工作区可被外部 Git 操作改变，必须以 HEAD hash、仓库 path、selected branch refs 作为结果落地身份；后置仓库/分支刷新若与快速轮并发，不能用同一 controller 内部 generation 相互取消，需区分任务代次或由统一协调器拥有取消权。

- 四项不宜无条件同时并行的主要原因不是 Git lock：各 Git 命令虽只读且使用 `--no-optional-locks`，但控制器读取的是不同时间的内部状态快照。仓库重扫完成后会发布总仓库列表并异步同步 HEAD；分支 force refresh 使用自身已消费的 repositories；提交读取使用当前 selected branches；status watcher 使用已有 HEAD slots。并发时后台仓库/HEAD/分支事件会引发第二轮读取并取消或覆盖第一轮，导致重复 I/O 和跨快照 UI，而非文件锁冲突。
