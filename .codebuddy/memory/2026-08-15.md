# 工作记录

- 子模块发现性能方案评估：可将当前逐层 `.gitmodules` 查询 + 每个子模块 `rev-parse` 的 BFS 改为单次 `git submodule foreach --recursive`。在 TypeScript `execFile` 中应把 foreach 的 shell 脚本作为单一参数传入，且输出用 `printf` 的 NUL 分隔并采用 `displaypath`，避免空格路径/递归相对路径解析歧义；仍需在返回结果中保留顶层仓库并从相对路径构造子模块绝对路径。`$path` 不宜作为长期接口，应优先 Git 提供的 `$sm_path`/`$displaypath`。

- 已将 `src/git/gitLogProvider.ts` 的 `collectSubmoduleRepositories` 改为对每个顶层仓库单次执行 `git submodule --quiet foreach --recursive "printf '%s\\0' \"$displaypath\""`；解析 NUL 输出后以顶层根目录解析绝对路径，并按最深包含路径重建子模块 `parentPath`，保留仓库列表和 `hasSubmodules` 语义。`npm run compile` 与该文件 TypeScript 诊断通过。

- 已将 `getGitBranches` 改为一次 `Promise.all` 并发执行 `git symbolic-ref --quiet --short HEAD`、本地 `git for-each-ref refs/heads` 和远程 `git for-each-ref refs/remotes`。本地/远程命令均返回 object id、短名和完整 ref 路径；当前分支从本地结果中提升为 `current` 项，detached HEAD 时不伪造当前分支。移除了分支下拉对 tags、单独 HEAD hash 和 refs 缓存的依赖，保留提交加载所需的 `getGitRefs`。`npm run compile` 通过；文件仅有既存未使用声明提示。

- 子模块扫描变慢的优化结论：当前 `submodule foreach --recursive` 会串行进入每个子模块执行 shell，且后续父级重建对每个路径全量 `filter + sort`，为 O(n² log n)。应优先恢复按层 `git config .gitmodules` + 同层 `rev-parse` 的并行发现；保留父级关系而非事后推导。随后将仓库扫描 single-flight 扩展到携带 `AbortSignal` 的调用（调用者取消等待而不取消共享扫描），并把 10 秒 TTL 改为拓扑变更事件失效。若保留 foreach，至少用目录祖先查找替代 O(n²) 父级重建，但其 Git 内部串行成本仍无法消除。

- 已实施子模块扫描优化：`collectSubmoduleRepositories` 恢复为逐层读取 `.gitmodules` 与同层 `Promise.all` 并发 `rev-parse`，发现时直接写入 `parentPath`。仓库缓存取消 10 秒 TTL，改为工作区/.gitmodules/显式 Git 操作调用 `invalidateGitRepositoriesCache()` 时失效；扫描按工作区 key 共享 in-flight Promise，调用者的 `AbortSignal` 只取消等待、不取消后台扫描，避免重叠刷新重复扫描。缓存失效版本号阻止旧扫描覆盖新拓扑缓存。`npm run compile` 通过；文件仅有既存未使用声明提示。

- 嵌套子模块扫描复核：当前按 BFS 层级 `await Promise.all` 的实现让第 N+1 层必须等待第 N 层所有兄弟仓库的 `.gitmodules` 查询和 `rev-parse` 全部结束；深层子模块因此被最慢无关兄弟阻塞。后续应改为任务递归/工作队列：一个仓库的 `.gitmodules` 结果一到便立刻启动其子模块扫描，不等待同层其他任务；子模块目录本身作为候选根立即递归，`rev-parse` 可并行做最终规范化。这样保留每个节点命令的并行性，同时移除跨分支的层级屏障。

- 已实施递归任务调度：`collectSubmoduleRepositories` 改为 `scanRepository` 递归展开，任一仓库 `.gitmodules` 结果一到即对每个子模块 `rev-parse`，命中新仓库立即登记 (`parentPath` 发现时写入) 并递归其子级，不再有 BFS 层间屏障；`scanTasks` Map 按 key 去重。当前按要求移除了 Git 调用并发上限，所有发现任务立即并发执行。TS 诊断通过，仅既存未使用声明提示。

- 分支加载慢的代码结论：`refreshSelectors` 以“加载分支”进度等待 `loadBranchesWithVirtualCommits`；后者虽并发读取分支，却同时等待 `getWorkingTreeChanges`。后者会并发执行 `git status --untracked-files=all`、`git diff --cached --raw/--numstat -M -C`、`git diff --raw/--numstat -M -C`，合计 5 条命令，并枚举全部未跟踪文件和变更元数据；大型工作区时它通常远慢于分支读取本身。分支读取仍会每次完整执行 `symbolic-ref`、本地 `for-each-ref`、远程 `for-each-ref`，没有分支缓存/单飞去重，远程 refs 多时也会明显变慢。

- 已确定分支加载优化方案：将 `getGitBranches` 与工作区虚拟提交的完整 Diff 元数据加载拆分。`refreshSelectors` 关键路径仅等待分支 refs，并先发布分支/提交；随后以当前刷新 generation 为保护异步加载 `getWorkingTreeChanges`，完成后只更新当前分支的 `virtualCommits` 与 Changed Files。可先用轻量 `getWorkingTreeChangePresence` 决定是否需要完整元数据读取；分支 refs 则加入按仓库 key 的 single-flight 缓存，并由现有 Git 状态变化触发失效。

- 已完成分支历史与虚拟提交解耦：`gitkViewProvider.ts` 的 `refreshSelectors`、`refreshCurrentHeadBranch`、`refreshBranchCommits` 均改为先仅调用 `getGitBranches`，随后同步读取/发布提交历史。新增 `loadVirtualCommits` 后台读取 `getWorkingTreeChanges`，完成后仅把 `virtualCommits` 附加到 `kind === 'current'` 的分支，并更新该分支的 staged/change 文件。发布条件只校验 `commitPageGeneration` 与当前分支 `name + hash`，不以仓库选择状态绑定；`rootUri` 仅用于执行工作树 Git 查询。`npm run compile` 和该文件诊断通过。

- 后续分支加载优化方向：当前 `readBranchRefsFromCli` 并发启动 `symbolic-ref`、`for-each-ref refs/heads`、`for-each-ref refs/remotes` 三个进程；可将本地和远程 refs 合并为一个 `for-each-ref refs/heads refs/remotes`，保留 `symbolic-ref` 并发，减少一次 Git 进程和 refs 扫描。另可为 `getGitBranches` 增加按仓库路径的 single-flight 缓存，沿用 Git 状态变化、fetch/pull/push 触发的失效机制。大量 refs 时仍需全量传给 Webview；若产品允许，可再延迟加载远程分支。

- 已完成 refs 加速：`readBranchRefsFromCli` 改为并发执行 `symbolic-ref` 与单次 `for-each-ref refs/heads refs/remotes`，再按完整 ref 前缀在 TS 内分类，Git 进程由 3 个降为 2 个。`getGitBranches` 新增按仓库路径的 bounded (20) 缓存与 in-flight 单飞，取消调用只取消等待；`invalidateGitRefsCache` 同步清理分支缓存并递增版本，防止 fetch/pull/push 或 watcher 触发后的旧请求覆盖新缓存。`npm run compile` 与 `gitLogProvider.ts` 诊断通过。

- 仓库/分支下拉加载文案统一简化：webview `setRepositoryLoading` / `setBranchLoading` 不再展示任何进度文案与计数（如“解析工作区文件夹/扫描子模块 (n/m)”），仓库显示栏仅显示“仓库名 + spinner”（无名称时固定“加载仓库...+spinner”）；弹窗统一为顶部 dropdown-progress 进度条 + 已选项单条带 spinner，空态为固定文案 + spinner，两个弹窗效果与加载逻辑完全一致。扩展端 `getGitRepositories` 的扫描进度消息仍走主进度条 (showLoadingProgress)，仅不再进入仓库下拉显示。`npm run compile` 通过。

- 提交历史性能结论：首屏请求仅 101 条提交，但 `readCommitsFromCli` 仍并发执行全量 `git for-each-ref refs/heads refs/remotes refs/tags` 以构造所有提交的 refs 映射；缓存未命中或超出 5 秒 TTL 时，refs 多/标签多的仓库会被该命令拖慢。默认 `selectedBranches = branches.map(...)` 会把全部本地和远程分支传入 `git log` 作为多个起点，也会增加可达图遍历成本。推荐先改为由同一 `git log` 的 `%D`/`--decorate` 只输出当前页提交的装饰信息，移除首屏全量 refs 扫描；默认视图改为当前分支（或 `HEAD`）历史，用户显式多选分支后才传多 refs。可选再将首屏从 101 降至 51 并后台预取下一页。

- 已完成提交历史加速：`readCommitsFromCli` 和 `searchCommits` 的 `git log --format` 新增 `%D`，解析器直接把当前页装饰 refs 写入 `GitCommit.refs`；已删除全量 `for-each-ref refs/heads refs/remotes refs/tags`、对应缓存及 refs→commit 映射构建，首屏/分页从两条 Git 命令降为一条。首次选择器加载改为仅选择 `kind === 'current'` 的当前分支，避免将全部本地/远程分支作为 `git log` 起点；用户后续显式多选仍保持原行为。`npm run compile` 及两处修改文件诊断通过。

- 提交历史后续优化建议：优先给 `getGitCommits` 增加按 `root + refs + skip + limit + refs-cache-version` 的短生命周期/单飞缓存，消除 watcher 连续刷新与重复选择的同页 log；随后精简首屏 `git log` 格式（延后或按需读取 body、committer、email），减少进程输出、解析和 Webview 序列化。多仓库模式应设置并发上限，避免同时执行大量 `git log` 导致磁盘争用；更进一步可将首屏压至 50 条并在空闲时预取下一页。

- 嵌套子模块扫描再次变慢的根因：递归任务虽移除了 BFS 同层等待，但每层仍是 `git config --file .gitmodules` → 对每个子模块 `git rev-parse --show-toplevel` → 发现后才调用子模块自身 `.gitmodules` 查询；深度为 D 的路径至少叠加 D 次 rev-parse 启动延迟。当前无限制并发还会令所有兄弟节点的 config/rev-parse 与深层链路争抢 Git 进程和磁盘。后续可直接将 `.gitmodules` 内解析出的绝对 `submodulePath` 当作子仓库根路径并立即递归扫描，移除每节点 rev-parse；失败/未初始化模块由其自身 `.gitmodules` 读取失败自然忽略。若必须保留根规范化，可使子级 config 扫描与其父级 rev-parse 并发而非串行。该递归可覆盖任意深度；无法消除的是每一层必须先读取父模块 `.gitmodules` 才能得知下一层路径的信息依赖，但移除 rev-parse 后每层仅余一次 config 查询。

- 进一步复核：不能仅以 `.gitmodules` 中的路径直接登记子仓库，因为该文件会声明未初始化子模块；直接递归会错误显示不存在的子仓库。安全的高收益方案是用异步文件系统检查子模块目录的 `.git` 文件或目录是否存在以确认 initialized，再直接读取/解析 `.gitmodules` 文本（或保留 `git config`），从而消除每个子模块的 `git rev-parse` 进程。更进一步可直接解析 `.gitmodules` 的 `[submodule "..."] path = ...`，将每个已初始化节点从两条 Git 进程降为零条 Git 进程；需妥善处理 Git 配置转义和 VS Code remote/workspace FS。

- 已完成子模块扫描降载：`collectSubmoduleRepositories` 保留 `git config --file .gitmodules`（继续由 Git 正确忽略注释并处理 config 转义），但以 `fs/promises.stat(<submodule>/.git)` 判断子模块已初始化，替换每个子模块的 `git rev-parse --show-toplevel`。新增 8 路 `createPriorityLimiter`，递归发现的子级 `.gitmodules` 查询和 `.git` 检查进入高优先队列，避免无限制进程风暴且不恢复 BFS 层屏障。任意深度递归仍由 `scanRepository(child, true)` 覆盖；`npm run compile` 与诊断通过。

- 已按用户要求恢复扫描方式：删除 `.git` 的 `stat` 判定，子模块路径重新使用 `git rev-parse --show-toplevel` 验证和规范化；保留递归任务与深层优先队列，避免恢复 BFS 层屏障。并发上限由固定 8 改为 `Math.max(1, os.cpus().length)`，即当前 Node 可见 CPU 线程数量。`npm run compile` 与 `gitLogProvider.ts` 诊断通过。

- 嵌套扫描后续优化：当前高优先队列采用 FIFO；宽层父模块一次入队大量子模块 `rev-parse` 后，最先验证成功子模块的 `.gitmodules` 任务仍会排在同层剩余 rev-parse 后面，深层链路无法立即穿透。可将递归发现的 `.gitmodules` 任务改为高优先 LIFO（栈）或按 depth 排序，优先推进已验证的深路径；为防止兄弟分支饥饿，可每处理 N 个深层任务后公平取一个普通任务。另可投机并发启动子目录 `.gitmodules` 查询与其 `rev-parse`，待父验证成功后再提交结果：可消除每层 config 等待，但需要丢弃未初始化/无效子模块的投机结果，复杂度与磁盘负载更高。

- 已实施嵌套扫描方案一：`createPriorityLimiter` 分为 normal FIFO、verification FIFO 和 deep LIFO 三类队列。子模块 `rev-parse` 进入 verification 队列，验证成功后递归的 `.gitmodules` 查询进入 deep 栈，因此深层链路会抢在同层剩余验证前继续推进；连续执行 8 个 deep 任务且存在非 deep 任务时强制让出一个名额，避免宽层兄弟饥饿。仍使用 `os.cpus().length` 并发上限和 Git `rev-parse` 验证语义；`npm run compile` 与诊断通过。

- 已按用户反馈撤回复杂调度：删除 CPU 并发限制、normal/verification/deep 队列、LIFO 与公平让出逻辑，恢复最简单的递归 `Promise.all` 展开。每个仓库读取 `.gitmodules` 后并行 `git rev-parse` 子模块，任一验证成功即登记并立即递归下一层；保留 path 去重、`parentPath` 与 Git 验证语义。`npm run compile` 和 `gitLogProvider.ts` 诊断通过。

- 当前直接递归的嵌套瓶颈：子模块自身 `.gitmodules` 查询需等待其 `rev-parse` 成功，深链仍形成 `父 config → 子 rev-parse → 子 config` 的层间串行门槛。下一步可采用简单投机并发：父模块获得 `submodulePath` 后同时启动该路径的 `resolveRepositoryRoot` 与 `getInitializedSubmodulePaths`；仅在 rev-parse 成功时登记子仓库并消费已完成/进行中的子 paths 继续递归，失败则丢弃投机 config 结果。这样保持 Git 对 initialized 的验证和 `.gitmodules` 解析，同时使下一层 config 与当前层验证重叠。

- 已实施嵌套扫描投机并发：`collectSubmoduleRepositories` 对每个声明的子模块同时启动 `getInitializedSubmodulePaths(submodulePath)` 与 `resolveRepositoryRoot(submodulePath)`；验证成功后将预先启动的 paths Promise 传给 `scanRepository` 复用，验证失败则不登记子仓库并丢弃结果。保留直接 `Promise.all` 递归、Git config 解析 `.gitmodules`、rev-parse initialized 验证、路径去重和 parentPath 语义；投机 Promise 预挂 catch 以防失败时未处理拒绝。`npm run compile` 与诊断通过。该方案在模块数量大时会为每个声明路径额外启动一次 `.gitmodules` 查询，即使模块未初始化或没有嵌套，导致进程数近乎翻倍并使扫描变慢；应回退到验证成功后再读取下一层的直接递归方式。

- 已优化子模块扫描：移除投机读取；`collectSubmoduleRepositories` 现在先通过 `git rev-parse --show-toplevel` 并行验证同层声明路径，只有验证成功、实际初始化的子模块才执行下一层 `.gitmodules` 查询。保留直接递归 `Promise.all`、路径去重及 `parentPath` 语义，避免未初始化/无嵌套模块触发多余 Git config 进程。`npm run compile` 与 `gitLogProvider.ts` 诊断通过。

- 虚拟提交点击文件慢点：`selectWorkingTreeChanges` 每次调用 `getWorkingTreeChanges`，其同时执行 `git status --untracked-files=all` 和 staged/unstaged 各两条 `git diff --raw/--numstat -M -C`，共 5 条命令；文件面板初始渲染只需要路径与状态。后续优化应为虚拟提交单独提供轻量文件列表读取，直接解析一次 `git status --porcelain=v1 -z --untracked-files=all` 的 staged/changes 路径和状态，省掉四条 Diff 元数据命令；若未来 UI 需要行数/二进制/精确重命名元数据，再按选中文件懒加载。

- Changed Files 与 CustomDiffPanel 联合优化：两者最终共享 `store.files`，但当前 `completeChangedFilesSelection` 等待 `DiffReader.prepare` 完成全部文件的分批读取后才打开 CustomDiffPanel，导致面板首个 Diff 被全部文件内容预热阻塞。联合方案应先用单次轻量 status 发布共享 `CommitFile[]` 清单，然后让 DiffReader 第一批仅读取首个选中文件；首文件 Diff 到达即打开 CustomDiffPanel 并写入共享 store，剩余文件在后台分批继续预热/更新进度。这样文件清单与首个 Diff 同时更快可见，同时仍保持双方共享同一 store 数据源。

- CommitFile 结构结论：不能直接移除 `CommitFile[]`，因为 `DiffPayload extends CommitFile`，且 `DiffReader.prepare` 需要 `path/status/oldPath/objectId/mode` 元数据构建工作树或提交 Diff。可在联合优化中移除 `stagedFiles`、`changeFiles`、`GitBranchVirtualCommit.files` 等重复持有的完整数组，仅保留共享 store 的一次 `CommitFile[] → DiffPayload[]` 渐进式状态和虚拟提交轻量 enabled 标记。
