## 修复: 外部命令行 commit 后提交列表不刷新 (src/git/eachRepoHeadBranchWatcher.ts)

**现象**: 外部终端 git commit 后, gitk 的 commit 列表不出现新提交(工作区未提交区会变, 提交列表不变)。

**根因链** (两处叠加, 都在 RepoHeadBranchWatcher):
1. `createHeadWatcher` 只监听 `.git/HEAD`。HEAD 存的是符号引用 `ref: refs/heads/x`,
   commit/amend/merge/rebase/reset 都只改写目标 ref 与 `logs/HEAD`, 不触碰 `.git/HEAD`
   (detached HEAD 除外)。所以 HEAD 值变化的信号源根本没进系统。
2. `getHeadBranchByRepo` 有 `if (cached) return cached;` 短路。唯一调用方
   `SelectedRepoTotalBranchWatcher.drainRefresh` 是在 refs 已被改写之后来取 HEAD 的,
   必然拿到旧 hash; 用它组装的 complete 快照与 previous 逐项 equals 相等
   (`GitBranchOption.equals` 比 hash) → `continue` → 不发 `onRepositoryBranchesChanged`
   → GitBranchesController 不 fireSelected → GitCommitController.selectBranches 不被调用。

**改动**:
- `getHeadBranchByRepo` 去掉缓存短路, 始终 `enqueueHeadRead` 取真值 (有 slot 合并 + needsRefresh 重跑)。
  缓存语义只保留给 `getCachedHeadBranch`(初始化回填场景)。
- `createHeadWatcher` pattern `'HEAD'` → `'{HEAD,logs/HEAD}'`。logs/HEAD 是 HEAD 移动的唯一权威记录;
  对 linked worktree 更是必需: `rev-parse --absolute-git-dir` 返回 `.git/worktrees/<name>`,
  而 `refs/heads/**` 在 common dir, SelectedRepoTotalBranchWatcher 的 refs watcher 在 worktree 下失效。

**收敛性论证**: logs/HEAD 若先于 ref 提交到达, 读到旧 H1 时 previous 也是 H1 → 不 fire; ref 事件
到达后 drainRefresh 读真值 H2 → fire。中间无倒退窗口。

**未改**: `GitBranchesController.applyTotalBranches` 的 fireSelected 判据仍是 headChanged
(选中非当前分支的 hash 变化不会下发给提交控制器) —— commit 场景下 HEAD 必然变, 已覆盖, 未扩大改动范围。

**内部 commit 原有路径保留**: gitkViewProvider.runCommit 仍显式
`uncommittedFilesWatcher.refreshHeadBranch()` + `commitController.forceRefreshCurrentSelection()`,
其必要性由"同步等新 HEAD 的 staged 清单就绪"支撑, 与本次 watcher 修复不冲突。

## 修复: 刷新提交按钮不刷新 unstaged/staged (未提交)

**现象**: 点 Commit 列表列头的刷新按钮, 只重跑 git log; Unstaged Changes / Staged Changes 两个虚拟行及其 Diff 正文不更新。

**根因**: 手动刷新链路是 `webview 'refresh' intent` → `store.dispatch` → `gitkViewProvider.refreshCurrentViewData()`
→ `commitController.forceRefreshCurrentSelection()` → `syncWorkingTreeForCurrentBranch(true)`
→ `uncommittedFilesWatcher.refreshUncommittedFilesByHeadBranch()` (置 `slot.fullRefreshPending`)
→ `refreshSlot()`。但 `refreshSlot` 里 `fullRefresh` 只作用于"跳过路径增量合并", **不参与
`contentChangedPaths`**; 而 `previousChanges?.equals(changes)` 命中时直接 return, 只发内容通道。
工作区文件没有 objectId(`git diff --raw` 对 unstaged 的 dst sha 恒为全 0), 内容变化不体现为清单变化,
于是整条链路一个事件都不发 → 下游 staged/unstaged 正文永不重读。

**改动**:
- `src/git/uncommittedFilesWatcher.ts` `refreshSlot`: `fullRefresh` 时把 `changes.staged + changes.changes`
  全部路径并入 `contentChangedPaths`, 让"强制全量"真正覆盖正文重读(状态清单变化时仍走状态通道, 不重复)。
- `src/webview/gitkViewProvider.ts` `refreshWorkingTreeDiffs`: 缓存键 `getWorkingTreeDiffCacheKey` 由清单元数据
  组成, 无法表达工作区内容, 内容重读后必须回写 `workingTreeDiffCache`, 否则切走再切回拿到旧正文。

**验证**: `npm run compile` 通过, 源码无诊断, `out/` 两条新注释均已落地。

## 刷新提交按钮: 追加异步重扫仓库与分支列表

**改动**: `gitkViewProvider.refreshCurrentViewData()` 开头追加两行, 与提交刷新并行、互不等待:
```ts
void this.requestRepositoryScan();                              // 首轮 initialize, 其后 submoduleWatcher.rescan()
this.selectedRepoTotalBranchWatcher.refreshSelectedRepositories(); // 每个选中仓库 enqueueRefresh(force=true)
```

**为什么可以并行而不必串行**: 重扫后 `SelectedRepoTotalBranchWatcher.syncRepositories` 对已有分支缓存的
仓库走 `needsFullRefresh = false`(`enqueueRefresh` 里 `if (!force && this.totalBranches.has(key)) return;`),
不会重读分支; 而新发现的仓库无缓存 → `needsFullRefresh = true` 会自动补齐。所以"先强制重读现有仓库分支,
再由 rescan 补齐新仓库"两者合起来是完整覆盖, 无需等 rescan 完成。

**并发安全**: `RepoSubmoduleWatcher.startQueuedScan()` 用 `rescanPromise` 合并重复请求,
`scan()` 开头 `if (this._isLoading) return this._totalRepoList;` 防重入; `rescan()` 只置
`fullRescanRequested = true`。`GitRepoController.reconcileSelection` 有 `hasUserSelection` 保护, 重扫不会覆盖用户选择。

**验证**: `npm run compile` 通过, 源码无诊断, `out/webview/gitkViewProvider.js` 已含新调用。

## 加载态改为"已选不变→顶部条, 已选变化→全屏蒙版"(覆盖上一条)

## 搜索行横向吸附: `position: sticky; top: 30px; left: 0`

**改动**: `#commitSearchRow` 的 sticky 增加 `left: 0`, 横向也吸在可视区左边缘, 进度条随之始终可见。

**为什么不用列头那套 `min-width: max-content`**:
- 列头撑得开是因为 `#commitHeaderColumns` 是与提交行**同模板的 grid**
  (`grid-template-columns: var(--main-width) var(--author-width) var(--hash-width) var(--date-width)`),
  四列宽变量由 `setColumnWidth()` **同时写到 `#graph` 和 `#commitList` 上**
  (`commitListSubPanel.ts:894-895`), 所以 `--author-width` 等不再是初始的 `max-content` 而是 `Nch`,
  列头的 max-content 因此等于整行宽 → 真的覆盖整条滚动宽。
- 搜索行没有这些列, 且 `#searchBox` 是 `flex: 1 1 auto; min-width: 0`, 整行 max-content 远小于列表,
  撑不出滚动宽; 就算用 `calc(var(--main-width) + var(--author-width) + ...)` 也不可行 ——
  变量初始值是 `max-content` 关键字, 不能进 `calc()`。
- 横向 sticky 不需要元素比可视区宽: sticky 的位移上界由滚动容器的可滚动溢出区决定(纵向 top 吸附同理),
  所以可视宽的元素也能被推到左边缘。副作用也更好: 搜索框不会被拉宽到滚动宽。

**验证**: `npm run compile` 通过, 零诊断; `out/` 正则校验 `position: sticky; top: 30px; left: 0` 已落地,
进度条仍在搜索行内。

**校验坑**: `out/` 被 .gitignore 覆盖, `search_content` 对 `out/**` 恒返回 0 条; 校验产物只能用 node。
另外 `s.indexOf('commitProgress')` 命中的是 CSS 段而非 markup, 判断挂载点要用顺序正则
(`/commitSearchRow[\s\S]{0,1500}commitProgress/` = true, `/codicon-repo-push[\s\S]{0,400}commitProgress/` = false)。

## 搜索也走顶部进度条: 标记从"就地重读"泛化为"不换数据源"

- `GitCommitController.refreshingCurrentSelection` / `isRefreshingCurrentSelection` 重命名为
  `inPlaceReload` / `isInPlaceReload`; 语义从"就地重读"泛化为"本次读取不换数据源":
  `forceRefreshCurrentSelection`(就地重读) 与 `search`(同一份已选上重新过滤) 都置位,
  `selectRepositories` / `selectBranches`(换数据源) 清零。
- `search()` 里 `this.inPlaceReload = true;` 必须在 `await this.refresh(false)` **之前**同步置位,
  因为 `refresh()` 一开始就同步 `loadingEmitter.fire(true)`, Provider 在那一刻读 `commitLoadingMode`。
- `doc/gitcommitcontroller.md` 同步补了 `isInPlaceReload`(状态表一行 + 接口声明一行)。
**验证**: `npm run compile` 通过, 零诊断; `out/` 校验 `inPlaceReload` 存在且 `refreshingCurrentSelection` 无残留。

## 搜索阶段文案: "正在搜索提交..."

- 布尔升级为单一状态枚举, 避免再加一个布尔与 `inPlaceReload` 打架:

  `search` 置 `'search'`, 两个入口 finally 回 `'rebuild'`。

  (否则 `stateUpdate.loadingMessage` 与 `loadingProgress.message` 会给出两套不同文案)。
